# 性能设计与耗时预算

本文件是 SKILL.md 的延伸阅读，解释「为什么快」以及各层机制的可调参数。
维护脚本前请先读这份，避免改动破坏已有的加速路径。

## 五层机制

1. **出口优选**：显式选择出网路径，并跳过不可达项（见 SKILL.md「出网出口」）。
   实测把出口从系统环境变量切到本机 Clash 后，rrdynb 文章页 4.03s → 1.56s
   且成功率 3/6 → 6/6；PanSou 冷搜索 52.9s → 13.1s。
2. **4xx 短路（rrdy）**：`403`（CF 拦截）/ `404` 等确定性错误立即返回，不重试。
   该站返回的 403 页面不含 Cloudflare 挑战特征串，原先会被误判为可重试错误，
   连续重试 3 轮 × 25s 超时，单次搜索实测 **70s**；短路后降至 **~2.7s**。
   PanSou 侧则相反：**仅当 4xx 响应体是 JSON**（确系 API 返回）才短路，
   HTML 错误页视为中间层瞬时故障继续重试。
3. **本地缓存**：
   - rrdy：HTTP 200 缓存 6 小时（`RRDY_OK_TTL`），确定性 4xx 缓存 10 分钟（`RRDY_NEG_TTL`）
   - PanSou：成功结果缓存 2 小时（`PANSOU_OK_TTL`），API 的 4xx 缓存 5 分钟（`PANSOU_NEG_TTL`）
   - 两者在网络级失败（HTTP 0）与 5xx 时**都不写缓存**，避免站点瞬时抖动被固化
   - 影视资源变化慢，2~6 小时的 TTL 换来的是「重复查询秒回」，值得
4. **端点不可用标记（rrdy）**：搜索接口在部分网络环境下恒定被 CF 拦截。
   一旦判定失败即写标记（默认 **6 小时**，`RRDY_SEARCH_BLOCK_TTL` 可调），
   期间换**新片名**也直接返回兜底地址，省去每次约 10s 的探测成本；
   搜索成功后立即清除。`--force-search` 可强制探测。
5. **并发 + 过期缓存兜底**：rrdy 多候选页用线程池并发（`--jobs`），取代原先的
   串行 + `sleep 0.8s`；pansearch 两源并行；网络抓取失败时自动回退到本地过期副本。

另外，`_addr_count()` 的 DNS 结果按主机缓存（pansou 与 rrdy 都有），
避免每次请求都白等一次 `getaddrinfo`。

## 耗时预算

| 脚本 | 参数 | 默认 | 作用 |
|---|---|---|---|
| pansearch | `--deadline` | 120s | 整条命令总预算 |
| pansou | `--deadline` / 搜索预算 | 120s / 100s | 总预算 / 单次搜索预算 |
| pansou | `--timeout` | 55s | 单次请求套接字超时 |
| rrdy | `--search-budget` | 12s | 搜索阶段预算 |
| rrdy | `--page-budget` | 30s | 单个文章页抓取预算 |
| rrdy | `--deadline` | 60s | 整条命令总预算 |

> 注：`urllib` 的 `timeout` 是**套接字级**超时，域名解析到多个 IP 时
> `socket.create_connection` 会逐地址尝试，实际阻塞可达 `timeout × 地址数`。
> 脚本在启用预算时按地址数均分剩余预算，因此总耗时可控。

### 超时参数为什么要按源分开

PanSou 的合理超时是 **55s**（服务端并发检索上百个频道与插件，慢但正常），
人人电影网是 **12s**（正常 2~8s）。两者差 4 倍，共用一个 `--timeout`
会出现「按 rrdy 习惯设 15s → PanSou 被误杀成不可达」的陷阱。因此：

```bash
pansearch.py "片名" --pansou-timeout 55 --rrdy-timeout 12   # 推荐
pansearch.py "片名" --timeout 15                            # 后备写法：同时设两者（小心）
```

## PanSou 首次查询为什么慢

**首次查询通常 12~45 秒**，偶发更久。这是服务端要并发检索上百个频道与插件，
延迟波动很大，属正常现象而非卡死。套接字超时特意设到 55s 就是为了
不误杀「慢但正常」的响应，总时长由 `--deadline` 兜底；命中缓存后为秒回。

`--cloud-types` / `--src plugin` **并不会显著加快**面板侧检索（过滤发生在服务端
收集之后），反而可能因范围过窄而漏结果。

## 实测记录（2026-10-07）

| 场景 | 耗时 |
|---|---|
| rrdy `search` 冷启动（未优化） | 70.3s |
| rrdy `search` 冷启动（4xx 短路后） | 2.7s |
| 端点标记命中后换新片名 | 0.78s（零网络请求） |
| 统一入口冷启动「三体」 | 32s → 9.68s（两源并行） |
| 热缓存（真·秒回） | 0.9s |

## 纯本地的后处理不产生额外耗时

以下几个环节全部在内存里完成，**不增加任何网络开销**，可以放心开启：

- 链接清洗、去重指纹、形态校验（`linklib`）
- `--min-score` 相关性过滤（`score` 排序时本来就要算）
- 同网盘聚类 `group_items` —— 只影响展示，**不会减少抓到的链接**
  （其余分享挂在代表条目的 `variants` 里）

## 多关键词时的预算怎么算

`pansearch.py "A" "B"` 逐个查询，**每个名称各获得一份完整的 `--deadline` 预算**，
总耗时约为 N × 单次。命中的缓存不会失效（两源缓存按关键词分开存），
所以重复跑过的片名几乎是秒回；想收紧单次预算就调小 `--deadline`。
